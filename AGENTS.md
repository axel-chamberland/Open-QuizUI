# AGENTS.md — Open QuizUI

Open WebUI tool/action function that renders interactive multiple-choice quizzes and flashcards — with spaced-repetition review (FSRS), in-page editing, results and download — as embedded HTML.

Machine-specific notes (environment, in-flight work) live in the gitignored `AGENTS.local.md`.

## Commands

```bash
pip install -e .        # Python deps (no requirements.txt); use a venv
npm ci                  # JS dev deps; its postinstall also fetches Playwright's Chromium
npm test                # Vitest (tests/*.test.js)
npm run test:python     # pytest (tests/test_*.py)
npm run test:all        # both
npm run build           # python backend/build.py — regenerates release/
npm run release         # test:all, then build (what CI/PR should end with)
```

## Build & release flow (important)

- `release/*.py` (action_function.py, tool.py) are **generated artifacts** — never edit them directly. Run `npm run build` after any change under `backend/`, `frontend/`, or the templates in `build.py`, and commit the regenerated files in the same commit. `.gitattributes` marks `/release/**` as linguist-generated.
- `backend/build.py` bundles `frontend/src/main.js` with esbuild, inlines `frontend/styles/base.css` and the bundle into `frontend/index.html`, and appends that document plus a generated `wrap_html()` to the backend Python. The output is a standalone single-file Open WebUI function.
- Anything in `backend/quiz_function.py` / `backend/quiz_tool.py` **after `def wrap_html(` is discarded by the build**; the Python source of truth is everything above that marker.
- `wrap_html()` is generated by build.py — changes to it in the backend files are overwritten. Its parameter list and the `__APP_DATA__` payload are hardcoded in `build.py`, so a setting that reaches the page means editing that template **and** `frontend/src/persistence/app_data.js`. Payload keys so far: `enableMathJax`, `mode`, `srsQueueSize`, `requestRetention`, `srsOnLoad`, `quiz`.
- User-facing settings (valves) live above the build cutoff and are preserved; edit them directly. Both backend files carry their own `Valves` class — keep the shared fields in sync when a setting applies to both — and the Action also carries a `UserValves` class.
- `THEMES` is a **single shared source in `backend/build.py` (`THEMES_SRC`)** — the backend files `from backend.build import THEMES`, and the build strips that import and injects the literal block after the imports, right before the main class. Theme edits go in `build.py`, not the backend `.py` files or CSS.

## Architecture

- `backend/quiz_function.py` — Action: a post-message button that parses free-form LLM output as a multiple-choice quiz or as flashcards (per its `parse_mode` valve) and renders it. Module docstring says `version: 3.0`; `pyproject.toml` (3.0.0) matches it.
- `backend/quiz_tool.py` — Tool: the same rendering, fed by a structured tool call. Its model-facing docstring is patched from `__getattribute__` (per `quiz_mode`, plus `enable_explanations`) while the tool is listed, where `__user__` is not available yet.
- The two backend files **duplicate** the shared logic (parsing, valves, theme plumbing) — no imports between them; a fix in one usually belongs in the other.
- `frontend/src/` — vanilla ES modules; no framework, and no bundler at dev time (esbuild runs only inside `build.py`):
  - `state.js`, `quiz.js` (flow), `srs.js` (FSRS scheduling), `timer.js`
  - `persistence/` — per-quiz browser storage, keyed by a content hash: `app_data.js` (the embedded payload plus runtime overrides), `progress.js`, `stats.js`, `question_order.js`, `question_removals.js`, `quiz_edits.js`
  - `rendering/` — `mcq.js`, `flashcards.js`, `results.js`, `editor.js`, `order.js`
  - `shared/` — `markdown.js`, `formatting.js`, `mathjax.js`, `clipboard.js`, `download.js`; `ui/` — `alert.js`, `events.js`, `fullscreen.js`, `rating_indicator.js`, `reportHeight.js`
- `frontend/index.html` is the dev entry (`python -m http.server` on `frontend/` serves it — module imports require HTTP, not `file://`) and holds the demo quiz. `examples/Feature_Showcase.html` is a saved copy of that page, published through GitHub Pages and linked from the README.

## Tests

- `tests/*.test.js` — Vitest; files opt into jsdom per-file via a `@vitest-environment jsdom` comment, and frontend modules are mocked for unit tests.
- `tests/browser.test.js` — the one real-browser file (`@vitest-environment node`): Playwright's Chromium, pinned exactly (`playwright` `1.62.0`) because a floating range could drift to a revision the browser cache does not have. `npm ci`'s postinstall downloads the browser; CI installs the system libraries it needs too.
- The page under test is what Open WebUI actually serves, not the dev entry: `tests/browser_page.py` runs `build()` and prints `wrap_html()`'s document for the JSON payload on stdin. It leaves the theme placeholders unreplaced — inject `THEMES[...]` from `build.py` for visual checks.
- `tests/test_*.py` — pytest: `test_action.py` / `test_flashcards.py` / `test_tool.py` (parsers, with per-message cases in `test_files/` and `test_files_flashcards/`), `test_meta_option_detection.py`, and `test_visual.py` (builds the release file, then drives the Action's valves and page payload).
- Tests write scratch output to `tmp/` (gitignored).

## Conventions

- Commit subjects use `feat:` / `fix:` / `refac:` / `minor:` / `test:` / `style:`, a short imperative subject, and a body that says what the problem was and what changing it does. One concern per commit, so a diff stays reviewable on its own.
- Don't bump versions as part of feature work: the version strings live in the module docstrings (`version: 3.0`) and `pyproject.toml` (3.0.0).

## Gotchas

- Python ≥ 3.12 (pyproject). CI uses Python 3.12 / Node 22; the docs claim 3.11 too — pyproject wins.
- CI (`.github/workflows/tests.yml`) runs `npm run test:all` only, and only for pushes to `main` / PRs targeting it — a `dev` push runs nothing — and it never verifies the build is fresh, so a stale `release/` from source changes passes CI unnoticed.
- No formatter is configured or pinned: no Python formatter is a dependency, and `npx prettier` fetches a version newer than most of the JS tree was written with, so keep touched files clean rather than reformatting wholesale.
- Spaced repetition imports `ts-fsrs@5.4.2` from jsDelivr at runtime, like MathJax, so both need Internet access. Offline, MathJax leaves LaTeX as plain text and starting review mode raises an alert that the library could not be loaded (`quiz.js`).
- Per-user valves are stored **per user**, not per chat (in Open WebUI: Chat Controls → Valves → Functions). The Action's `effective_valves()` layers only the fields a user actually set (`model_dump(exclude_unset=True)`) over the admin's `Valves`, so untouched fields — and users who never opened the panel — keep the admin's values. The Tool has no `UserValves`.
- repo remote is `Open-QuizUI` (`git@github.com:axel-chamberland/Open-QuizUI.git`), while backend docstrings reference `OpenQuizUI` GitHub Pages — docs are in `docs/` (Home, Getting-Started, Usage, Customization, Formatting, Troubleshooting, Development, Contributing).
- This project doesn't vendor Open WebUI. To verify Open WebUI internals (Functions/Tools API, valves, event emitters) against the real project, consult upstream: the `open-webui/open-webui` repo and openwebui.com/docs. Any local reference checkout stays gitignored and uncommitted.
